# CLAUDE.md

Постоянные правила для всех будущих сессий работы над этим репозиторием.
Контекст продукта, полная архитектура и обоснования — в `./docs/`. Этот
файл — только оперативные правила «как делать», не «почему». При конфликте
между этим файлом и `./docs/` — `./docs/` источник истины по архитектуре,
этот файл — по процессу; расхождение чинится обновлением обоих.

## Стек и версии

- Astro 5, TypeScript `strict: true` (см. `docs/01-stack-adr.md` — полное
  обоснование выбора)
- Tailwind CSS (токены — `docs/04-design-system.md`, зеркалятся в
  `tailwind.config.ts`)
- React 19 (было 18, апгрейд август 2026 — см. `docs/01-stack-adr.md` и
  `docs/10-quality-gates.md` §2.1) — **только** внутри `client:*`
  островов, никогда в общем layout
- Astro Content Collections + Zod-схемы — весь текстовый контент
- Supabase (Postgres + Auth + RLS), регион EU (Frankfurt) — только для
  account-based инструментов (трекер занятий, карта зон), подключается Ф4
- Cloudflare Pages + Pages Functions — хостинг
- Vitest — unit-тесты; Lighthouse CI — пороги производительности/SEO/a11y
  (`docs/10-quality-gates.md`)

## Структура папок

```
src/
  pages/lv/...          # LV-дерево URL, файловый роутинг Astro
  pages/ru/...          # RU-дерево URL, независимое от lv/
  content/pages/{lv,ru}/  # MDX-контент статей, связан с pages/ по route_id
  content/theory-questions/  # банк вопросов тренажёра
  components/layout/    # Header, Footer, PhaseBar, *Template.astro — без интерактива, кроме PhaseBar
  components/content/   # Callout, StepList, Checklist, DataFreshness, FAQ
  components/tools/{tool-slug}/  # один инструмент = одна папка = один остров
  lib/state/             # nanostores (phase.ts и т.д.)
  lib/{wizard,calculator,ratings,decoder,simulator,deadlines,apply}/  # формулы, один модуль на инструмент
  types/                 # TypeScript-типы данных (docs/03-data-model.md)
  schemas/               # Zod-эквиваленты типов
docs/                    # архитектура, контракты, backlog — не трогать без обновления при изменении кода
fixtures/                # мок-данные, валидные по schemas/, используются в dev и unit-тестах
scripts/                 # check-bundle-budget.ts, check-i18n-coverage.ts, compute-ratings.ts
```

## Соглашения об именах

- Файлы серверных компонентов — `PascalCase.astro`; острова —
  `PascalCase.tsx`.
- `route_id` — `kebab-case`, совпадает буквально со строкой в
  `docs/02-routes.md`; используется как есть в аналитике, тестах, frontmatter.
- Ветки — `phase/{Ф-номер}-{T-id}-{краткое-описание}`, например
  `phase/f1-t033-calculator-formula`.
- Коммиты — императив, без префиксов-эмодзи, с явной ссылкой на задачу:
  `T-033: реализовать computeCalculator и unit-тесты`.
- Zod-схема данных — `{TypeName}Schema` в `src/schemas/{typeName}.ts`,
  один файл на источник данных из `docs/03-data-model.md`.

## Как добавить новую страницу

1. Найти или добавить строку в `docs/02-routes.md` — `route_id`, путь LV,
   путь RU, тип, шаблон, фаза, инструмент (да/нет), источник данных. Если
   строки ещё нет — сначала PR в `docs/02-routes.md`, отдельно от кода.
2. Создать `src/content/pages/lv/{route_id}.mdx` и (если контент готов на
   оба языка) `src/content/pages/ru/{route_id}.mdx` с frontmatter
   `route_id`, `lang`, `title`, `description`. **Если перевода ещё нет —
   не создавать RU-файл-заглушку.** Страница на этом языке просто не
   существует до перевода (правило 7.3 Модуля 7, детали —
   `docs/07-i18n-seo.md` §2). `LangSwitch` сам покажет состояние `disabled`.
3. Создать `src/pages/lv/{...путь...}.astro` (и `ru/`, если контент готов),
   использующий нужный `*Template.astro` из `docs/05-components.md`.
4. Если у страницы есть инструмент — см. раздел «Как добавить новый
   инструмент-остров» ниже, **до** шага 3.
5. Прогнать `npm run check` локально — особенно `i18n:coverage` (сообщает,
   если пара языков не совпадает с ожиданиями) и `budget` (JS-страницы ≤60KB
   gzip, если это не страница инструмента).
6. Обновить статус строки в `docs/02-routes.md` на «в проде» **в том же PR**.

## Как добавить новый инструмент-остров

1. Контракт — **сначала документ, потом код**. Если это один из 15
   приоритетных инструментов — файл уже должен существовать в
   `docs/06-tools/`; если инструмент лёгкий (не в списке 15) — контракт
   фиксируется прямо в тексте задачи `docs/11-backlog.md` (см. правило
   решения в конце `docs/05-components.md`).
2. Формулы (если есть) — чистые функции в `src/lib/{tool}/`, **без** React,
   покрыты unit-тестами на данных из `/fixtures/` до того, как пишется UI.
3. UI — `src/components/tools/{tool-slug}/`, компонент оборачивается в
   `ToolShell` (docs/05-components.md §4), гидратируется `client:visible`
   по умолчанию (не `client:load`, кроме `PhaseBar` — это не инструмент).
4. Проверить в DevTools → Network на **соседней** странице, что chunk
   нового инструмента там не подгружается — это не опция, а гейт
   (`npm run check` → `budget`).
5. Добавить события аналитики по таблице `docs/08-analytics.md` §2 (если
   инструмент участвует в лестнице микроконверсий) — событие пишется в
   Слой Б (docs/08 §1), не в Слой А.
6. Реализовать все применимые состояния из `docs/04-design-system.md` §5.
7. Добавить строку в таблицу `docs/05-components.md` §4, если инструмент —
   один из приоритетных пятнадцати.

## Что НИКОГДА не делаем

Перенесено из раздела 7.7 Модуля 7 — это не эстетические предпочтения, у
каждого пункта есть обоснованная причина, менять список можно только через
явное решение продукта, не через «здесь особый случай»:

| Никогда | Почему |
|---|---|
| Поп-ап с формой через 15 секунд | Тревожная аудитория закрывает вкладку |
| Чат-бот с «Здравствуйте! Чем помочь?» | Человек ищет информацию, а не разговор |
| Счётчик «осталось 2 места в группе» | Ложная срочность → потеря доверия |
| Личный кабинет как условие доступа к тренажёру | Обрыв на самом ценном шаге — тренажёр работает без регистрации по дизайну (Ф1) |
| Отдельный раздел «Блог» как свалка | Всё, что стоит писать, имеет своё место в дереве (`docs/02-routes.md`); блог (Ф5) — только новости изменений правил, не общая рубрика |
| Слайдер на главной | Никто не листает, убивает LCP |

Дополнительно, выведено из принципов проекта и подтверждено архитектурой
(не должно быть переоткрыто без пересмотра `docs/01-stack-adr.md` и
`docs/00-assumptions.md`):

- Не подкручивать цену/позицию партнёра (FORS) визуально или в данных —
  единственная защита продукта. Любой PR, меняющий стиль строки партнёра
  относительно конкурентов в калькуляторе/каталоге/рейтинге, — automatic
  reject на review.
- Не добавлять `is_partner: true` школе без закрытых юридических пунктов
  из `docs/09-legal-gdpr.md` (согласие/DPA/privacy policy) — техническое
  поле напрямую привязано к юридическому статусу.
- Не выдумывать число при отсутствии данных — см. правило пустых данных,
  `docs/03-data-model.md`, вступление.
- Не тянуть JS инструмента на страницы, где он не используется — контроль
  через `npm run check` → `budget`, не «разработчик обещает быть аккуратным».
- Не менять формулу рейтинга (`wilsonLowerBound`) вне ETL-скрипта
  `scripts/compute-ratings.ts` и вне code review — рейтинг не редактируется
  вручную никем.

## Правило: одна задача — один коммит — обновлённый backlog

Каждый `T-xxx` из `docs/11-backlog.md` — один PR, один (или несколько
логически неделимых) коммит(ов) с явной ссылкой на ID задачи. PR не
мержится, если после него `docs/11-backlog.md` не отражает завершение
задачи, а `docs/02-routes.md` (если PR затрагивал маршруты) не обновлён.
Задача считается сделанной только при выполненном Definition of Done из её
описания в backlog — не по ощущению «в целом готово».

## Git: репозиторий и обязательный PR-флоу (с T-006c, сентябрь 2026)

Репозиторий — `github.com/operkot1/macibu` (публичный, см. `docs/11-backlog.md`
T-006c про причину публичности). `main` защищён branch protection
(`enforce_admins: true`, обязательный статус-чек `check`) — **прямой push
в `main` больше не проходит физически, включая от владельца репозитория**.
С этого момента любой коммит идёт так: ветка `phase/{Ф-номер}-{T-id}-...`
→ `git push -u origin <ветка>` → `gh pr create` → дождаться зелёного `check`
→ `gh pr merge --merge --delete-branch` → `git checkout main && git pull`.
Прежние коммиты в истории сделаны напрямую в `main`, потому что удалённого
репозитория ещё не существовало — это не прецедент, воспроизводить не надо.
