# 07. Двуязычие и SEO

## 1. Где хранятся переводы

Content Collections, раздельные файлы на язык, связанные общим полем
`route_id` (совпадает с docs/02-routes.md), не общим объектом с двумя
языковыми полями внутри одного файла:

```
src/content/pages/
  lv/
    p1-celvedis.mdx     # frontmatter: { route_id: "p1-celvedis", lang: "lv" }
  ru/
    p1-celvedis.mdx     # frontmatter: { route_id: "p1-celvedis", lang: "ru" }
```

Причина раздельных файлов, а не одного двуязычного: переводчик/редактор
работает с одним языком за раз в CAT-подобном воркфлоу (см. открытый вопрос
В-5, docs/00-assumptions.md), и git-diff на PR перевода не задевает
исходный LV-файл.

## 2. Как связаны LV/RU версии одной страницы

Через `route_id`, не через путь. Скрипт `scripts/check-i18n-coverage.ts`
(часть `npm run check`, docs/10-quality-gates.md) на каждый `route_id` из
реестра docs/02-routes.md со статусом `план`→после реализации проверяет:

- если файл `lv/{route_id}.mdx` существует, но `ru/{route_id}.mdx` — нет:
  **не ошибка сборки**, а предупреждение в отчёте (страница в разработке),
  RU-URL для этого route_id **не генерируется** (не 404 руками, а просто
  отсутствует в роутинге Astro — там нет файла, значит нет страницы);
- `LangSwitch` (docs/05-components.md) для такой страницы получает
  `alternateUrl: null` и рендерится в состоянии `disabled` с текстом «Страница
  пока недоступна на русском» — **не** скрывается и не ведёт на перевод
  через машинный translate;
- обратное — RU есть, LV нет — обрабатывается симметрично (актуально для
  EN-хаба Ф5, где может быть наоборот).

Это прямая реализация правила Модуля 7: «либо переводим, либо страницы нет»
— никогда не показываем LV-контент на RU-URL и не подписываем его как
перевод.

## 3. hreflang

Каждая страница, у которой есть обе версии, получает в `<head>`:

```html
<link rel="alternate" hreflang="lv-LV" href="https://example.lv/lv/.../" />
<link rel="alternate" hreflang="ru-LV" href="https://example.lv/ru/.../" />
<link rel="alternate" hreflang="x-default" href="https://example.lv/lv/.../" />
```

`ru-LV`, не `ru-RU` — аудитория русскоязычная в Латвии, не Россия (это
явно задано Модулем 7 и совпадает с реальным геотаргетингом продукта).
`x-default` всегда указывает на LV-версию (правило 7.3). Если пары нет —
блок `hreflang` для этой страницы содержит только один `<link
rel="alternate">` на себя же плюс `x-default` (не на несуществующую
RU-страницу).

Домен — плейсхолдер `https://example.lv`, см. `A-06`/открытый вопрос В-4 в
docs/00-assumptions.md, заменяется одним значением в конфиге при появлении
реального домена.

## 4. Canonical

Самоссылающийся `<link rel="canonical">` на **каждой** странице, включая
страницы с фильтрами (canonical таких страниц указывает на базовый URL без
параметров, см. §6). Без кросс-языковых canonical — LV и RU версии не
canonical друг друга, это разные страницы для разных аудиторий, не дубли.

## 5. sitemap.xml по языкам

Три файла: `sitemap-lv.xml`, `sitemap-ru.xml`, `sitemap-index.xml`
(индекс, ссылающийся на оба). Генерируются на сборке из фактически
существующих файлов Content Collections (не из полного реестра
docs/02-routes.md — реестр содержит и ещё не реализованные route_id).
Каждая запись `<url>` включает `<xhtml:link rel="alternate">` на пару, если
она есть — так поисковик получает hreflang-сигнал напрямую из sitemap, не
только из `<head>` каждой страницы.

Динамические маршруты (`school-card`, `blog-post`) — их URL добавляются в
sitemap по данным (`schools.json`/посты блога), а не как один шаблонный
URL. `/kategorijas/*` — не в sitemap до Ф5 (страниц физически нет, см. `D-04`
в docs/02-routes.md).

## 6. Фильтры каталога и других инструментов

Правило 7.3: «инструменты — без пагинации и параметров в индексе». Реализация:

- Фильтры `p3-katalogs`, `p3-reitings`, `p3-instruktori` передаются как
  query-параметры (`?city=riga&gearbox=manual`), состояние живёт в URL для
  шэринга ссылки с уже применёнными фильтрами.
- Любая непустая комбинация параметров получает `<meta name="robots"
  content="noindex, follow">` — `follow`, чтобы поисковик всё равно обходил
  ссылки на карточки школ внутри отфильтрованного списка, просто не
  индексировал саму страницу-с-фильтром как отдельный документ.
- `canonical` отфильтрованной страницы указывает на неотфильтрованный
  базовый URL того же каталога (не на произвольную «похожую» комбинацию).
- Форма записи (`apply-index`) состояние в query не хранит вовсе (см. `A-08`,
  docs/00-assumptions.md) — по умолчанию нет риска индексации промежуточных
  состояний формы.

## 7. robots.txt

Единый файл (не по языкам), запрещает обход `/pieteikties/*` (форма —
незачем индексировать, целевая ценность не в её тексте) и `/*?*` эвристически
не блокируется целиком (это заблокировало бы легитимные canonical-варианты
у краулеров, которые не читают meta robots) — вместо `Disallow` для query-
строк используется **только** meta `noindex` (§6), чтобы Google мог
обойти страницу, увидеть noindex и корректно не проиндексировать её, но не
терял возможность дойти по ссылкам дальше. Явно прописан `Sitemap:
https://example.lv/sitemap-index.xml`.

## 8. Schema.org

| Тип страницы | Разметка |
|---|---|
| Гайды/HowTo (`p1-celvedis`, `p1-baltas-ka-sanemt`, `p5-csn-negadijums`, любая страница с `StepList interactive`) | `HowTo` |
| Страницы с компонентом `FAQ` | `FAQPage` (генерируется автоматически из `FAQProps.items`, не дублируется вручную) |
| `school-card` / `school-card-fors` | `LocalBusiness` (+ `AggregateRating`, только если у школы есть запись в `ratings` с `confidence !== "insufficient"` — не публикуем `AggregateRating` schema для недостоверной выборки, это ввело бы поисковик в заблуждение так же, как пользователя) |
| `p3-katalogs`, `p3-reitings`, `p3-instruktori`, `cat-*` | `ItemList` |
| `blog-post` | `Article` |

Разметка генерируется в `ArticleTemplate`/`ToolPageTemplate`/`SchoolCardTemplate`
из типизированных пропсов компонента, не пишется вручную в MDX — иначе
рассинхронизация контента и структурированных данных неизбежна.

**Найдено при ревизии кода (август 2026):** все места, вставляющие
JSON-LD (`CatalogTemplate`, `SchoolCardTemplate`, `BlogPostTemplate`,
`HowToSchema`, `ItemListSchema`, `FAQ`), использовали `set:html={JSON.
stringify(x)}` напрямую — `JSON.stringify` не экранирует `<`, а значит
строковое значение внутри объекта, буквально содержащее `</script>`,
разорвало бы тег и позволило вставить произвольный HTML/JS. Практический
риск был низким (данные редакционные/плейсхолдер), но это стандартная,
бесплатная защита (рекомендация OWASP). Исправлено: общий хелпер
`src/lib/seo/toSafeJsonLdString()` (`src/lib/seo/safeJsonLd.ts`, покрыт
`safeJsonLd.spec.ts`) экранирует символ `<` в строку `\u003c` перед
вставкой — **любой новый компонент, вставляющий JSON-LD, обязан
использовать этот хелпер, не голый `JSON.stringify`**.

## 9. EN-хаб (Ф5)

`/ka-iegut-tiesibas/arzemniekiem/english/` и `/kak-poluchit-prava/inostrancam/english/`
— обе ведут на общий `/en/` хаб (третье, ограниченное языковое дерево, вне
скоупа Ф0–Ф4). До Ф5 эти два route_id существуют как обычные LV/RU-страницы-
заглушки с объяснением «English version coming soon» — не как рабочий `/en/`
раздел с hreflang `en`. Полноценный hreflang `lv-LV ↔ ru-LV ↔ en ↔ x-default`
проектируется отдельно при подходе к Ф5, не сейчас.
