# 09. Юридическое и GDPR

## БЛОКИРУЮЩЕЕ ПРАВИЛО

`/pieteikties/` (`apply-index`, `apply-fors`) **не выкатывается в прод**, пока
не закрыты все три пункта ниже. Это жёсткое условие в Definition of Done
задач Ф3 в docs/11-backlog.md, не пожелание. Партнёрская модель = передача
персональных данных лида третьим лицам (школам-партнёрам) — за нарушение в
Латвии штрафует **Datu valsts inspekcija**.

1. **Явное согласие с перечислением получателей.** Чекбокс на форме записи
   не может звучать общо («согласен на обработку данных») — он обязан
   перечислять конкретных получателей (на старте — Autoskola FORS, по имени)
   или явно указывать, что получатель определяется автоматически по
   введённым критериям (город/категория) и называется пользователю **до**
   отправки формы (список «Подходят 3 школы» на Экране 6 уже показывает
   получателей до клика «Отправить» — это правильный паттерн, чекбокс должен
   на него ссылаться, а не дублировать текст).
2. **Договор о совместной обработке данных с каждой школой-партнёром**
   (Art. 26 GDPR — joint controllers, либо Art. 28 — processor agreement,
   в зависимости от того, кто фактически определяет цели обработки; для
   партнёрской маршрутизации лида обычно применим совместный контроль,
   решение — за юристом, не за инженером). До подписания договора с
   конкретной школой её `is_partner` не может быть `true` в `schools`
   (docs/03-data-model.md) — техническое ограничение прямо привязано к
   юридическому статусу, не к желанию партнёрского менеджера ускорить запуск.
3. **Политика конфиденциальности** (`privacy`, docs/02-routes.md) — должна
   существовать и быть опубликована **до** первого визита на `apply-*`, не
   «скоро будет». Содержит минимум: кто оператор (см. открытый вопрос В-2,
   docs/00-assumptions.md — сейчас плейсхолдер `[ЮРЛИЦО TBD]`), какие данные
   собираются на каждой ступени лестницы микроконверсий (docs/08-analytics.md),
   сроки хранения, права субъекта данных (доступ/удаление/возражение), контакт
   для обращений, ссылка на Datu valsts inspekcija как надзорный орган.

**Уточнение (T-060, найдено при инвестигации):** пункт 2 — про `is_partner`
в **реальном** источнике данных (`schools.json` после реального ETL из
CSDD-выгрузки/анкеты онбординга, docs/03-data-model.md). `fixtures/
schools.json` — dev/mock-данные для сборки и проверки UI до появления
реальных данных (тот же принцип, что во всём остальном проекте, см.
CLAUDE.md), правило на них не распространяется: `/pieteikties/` физически
не задеплоен (маршрута ещё нет), лид никуда не уходит ни при каком
состоянии фикстуры. Решение подтверждено пользователем в сессии T-059/
T-060.

## Несовершеннолетние пользователи

Визард (`wizard`) явно предлагает возрастную группу `"16-17"` — то есть
портал заведомо обрабатывается несовершеннолетними. Латвийское
законодательство о минимальном возрасте самостоятельного согласия на
обработку данных информационного общества (аналог GDPR Art. 8) должно быть
сверено юристом отдельно. **До этой сверки** — по умолчанию для
`age_bracket: "16-17"` ступени 3 и выше (email, аккаунт, заявка) не должны
включать сбор данных без дополнительного шага, явно упоминающего согласие
законного представителя, если возраст ниже установленного законом порога.
Технически это означает: `age_bracket` из `wizard_result`, если он попадает
в `user_state`, должен быть доступен форме записи для отображения
предупреждения — не для блокировки (блокировка по возрасту — решение
юриста, не инженера), а для корректного текста согласия.

## UGC (карта экзаменационных зон, Ф4)

Каждая запись `exam_zones` с `submitted_by: "ugc"` технически связана с
отправителем (даже если анонимно на UI) для модерации/защиты от спама.
Требуется: политика хранения IP/идентификатора отправителя отдельно от
публично видимой метки на карте, право на удаление собственной метки по
запросу (Art. 17 GDPR — right to erasure), явный порядок модерации (см.
docs/06-tools/karta-zon.md).

## Технические меры (Supabase RLS) как часть юридического контура

RLS-политика `user_id = auth.uid()` на `user_state` — не только защита
доступа, но и техническая мера, которую нужно упомянуть в политике
конфиденциальности как обеспечивающую изоляцию данных между пользователями.
Любое изменение RLS-политики — событие для security review (см. риски,
docs/00-assumptions.md), не рядовой PR.
