# 01. ADR: выбор технологического стека

Статус: **Принято**. Дата: 2026-08-02. Автор: тимлид проекта.

## Контекст

Портал — ~150 URL на двух языках, преимущественно контентные страницы
(гайды, справочники, карточки школ), плюс 15+ интерактивных инструментов
разного веса (от лёгкого калькулятора до трекера занятий с аккаунтом и
Supabase-хранилищем). Требования, продиктованные продуктом:

- SEO критичен — портал живёт с органического трафика по обоим языкам.
- Максимум JS на контентных страницах (бюджет 60 KB gzip, см.
  docs/10-quality-gates.md) — большинство посетителей никогда не откроют
  инструмент.
- Часть функциональности (трекер занятий, карта зон, отзывы) требует аккаунта
  и персональных данных с RLS — это принципиально другой профиль (динамика,
  запись, приватность), чем у справочника штрафов.
- Двуязычие — не переключатель, а два дерева URL с hreflang.
- Изменение цены/рейтинга в реальном времени не требуется — данные CSDD
  обновляются периодической выгрузкой (xlsx/csv), не live-потоком.

Главный архитектурный риск, который прямо назван в задаче: **не дать одному
инструменту с аккаунтом превратить весь сайт в динамическое SSR-приложение.**
Если это случится, каждая контентная страница (справочник знаков, гайд по
медсправке и т.д.) тоже начнёт рендериться на сервере при каждом запросе или
тянуть клиентский JS-раннер уровня SPA — это прямое нарушение бюджета
производительности и цели SEO.

## Рассмотренные варианты

### Вариант А — Astro 5 + TypeScript strict + Tailwind + React-острова (гипотеза)

- Контентные страницы (~85% дерева) — статический HTML, ноль JS по умолчанию.
  Astro рендерит компоненты в HTML на сборке/на границе и не отправляет их
  JS-рантайм клиенту, если это не остров.
- Каждый инструмент — самостоятельный React-остров (`client:visible` /
  `client:idle`), гидратируется независимо, не тянет за собой рантайм других
  инструментов и не заставляет соседние контентные страницы становиться
  динамическими.
- Content Collections — типизированный слой для статей/справочников
  (frontmatter validated by Zod schema на сборке — опечатка в поле фазы или
  дате не пройдёт `astro build`).
- Supabase подключается **только из тех островов, которым это нужно**
  (трекер занятий, карта зон, отзывы, сохранение пути). Остальные 140+
  страниц ничего не знают о Supabase и не делают к нему запросов.
- i18n через файловую структуру `src/pages/lv/...` и `src/pages/ru/...` —
  два дерева, как того требует принцип 7.1, без параметра `?lang=`.

### Вариант Б — Next.js (App Router) + SSG/ISR

- Технически способен на то же самое: статическая генерация, React Server
  Components без клиентского JS по умолчанию, `"use client"` острова для
  интерактива, i18n через сегменты `[lang]`.
- Обратная сторона: RSC-модель Next.js по умолчанию тяготеет к серверному
  рендерингу и рантайму Node на границе (даже для «статических» страниц
  через revalidate/ISR часто заводится серверная функция). Держать дисциплину
  «эта страница обязана быть чистым HTML без сервера» в Next.js требует
  постоянного контроля конфигурации (`output: 'export'` конфликтует с частью
  App Router фич, которые понадобятся позже — Route Handlers для форм,
  middleware для hreflang-редиректов).
- Экосистема шире (больше библиотек, больше Stack Overflow), но для этого
  проекта не даёт преимущества — инструментов немного (15), их можно написать
  как обычные React-компоненты в любом фреймворке.
- Next.js отлично подходит, когда **бóльшая часть сайта** — приложение
  (дашборд, личный кабинет). Здесь всё наоборот: 85% сайта — контент, 15% —
  инструменты. Плата за App Router (рантайм, размер бандла, сложность
  кеширования) распределяется на весь сайт, даже на страницы, которым она не
  нужна.

## Как вариант А отвечает на главный риск («не дать одному инструменту с
аккаунтом сделать весь сайт динамическим»)

1. **Единица гидратации — остров, а не страница.** Добавление аккаунта в
   трекер занятий не меняет ничего в том, как рендерится `/lv/eksmu-vaditajs/sodi/`.
   Между ними нет общего рантайма, только общий дизайн-система (CSS-токены,
   которые не требуют JS).
2. **Supabase-клиент не глобальный.** Он импортируется точечно внутри острова
   (`TrackerWidget.tsx`, `ExamZoneMap.tsx`, `SaveMyPathButton.tsx`), а не в
   корневом `Layout.astro`. Если завтра инструмент с аккаунтом исчезнет —
   удаление одного файла не затрагивает сборку остальных 150 страниц.
3. **Аутентификация не в layout.** `PhaseBar` (см. docs/05-components.md)
   читает состояние «где ты сейчас» из `localStorage`/cookie без аккаунта —
   это неавторизованная персонализация. Авторизация нужна только внутри
   конкретных account-based островов (Ф4), не для базовой персонализации
   навигации.
4. **Правило в quality gates (docs/10):** «JS на контентной странице ≤ 60 KB
   gzip; инструмент грузится только на своей странице» — это не благое
   пожелание, а проверяемый CI-гейт (`npm run check` считает бандл каждой
   страницы). Регрессия ловится до мержа, а не на проде.

## Хостинг: Cloudflare Pages (выбрано) vs Vercel

Оценивалось без внешних ограничений (нет существующего аккаунта или
обязательств — подтверждено заказчиком), только по техническим критериям.

| Критерий | Cloudflare Pages + Workers | Vercel |
|---|---|---|
| Поддержка Astro (SSG + islands) | Официальный адаптер `@astrojs/cloudflare`, зрелый | Официальный адаптер `@astrojs/vercel`, зрелый |
| Периферия/латентность для LV-аудитории | Много PoP в ЕС, включая Ригу/Франкфурт | Сопоставимо, тоже сильная EU-периферия |
| Данные и функции в EU-юрисдикции | Явный контроль региона для Workers/D1 при необходимости | Возможен через Enterprise-конфигурацию, по умолчанию глобальный роутинг |
| Стоимость на масштаб ~150 статических страниц + редкие функции (форма записи, ETL-триггер) | Практически бесплатно на free-тир (unlimited static requests) | Free-тир жёстче ограничивает функции/билд-минуты при росте трафика |
| Совместимость с Supabase (просто HTTPS API) | Нет зависимости от рантайма хостинга — Supabase есть отдельно в любом случае | Так же нет зависимости |
| Риск vendor lock-in под конкретные Next.js-фичи | Низкий — используется общий адаптер Astro | Низкий, но исторически Vercel теснее всего интегрирован с Next.js, что не используется |

**Решение: Cloudflare Pages.** При равной технической пригодности он дешевле
на статически-тяжёлом сайте (a это 85% этого проекта), даёт более прямой
контроль над регионом выполнения edge-функций (форма записи, редиректы
hreflang) — что читается как более консервативный выбор с точки зрения GDPR
(данные и функции ближе к ЕС по умолчанию), и не тянет за собой Next.js-специфичные
допущения, которые здесь не нужны. Решение обратимо: Astro не привязывает к
хостингу намертво, смена адаптера — это конфиг, а не переписывание кода.

## Итоговый стек

| Слой | Технология | Причина |
|---|---|---|
| Фреймворк | Astro 5 | Контент = статика по умолчанию, острова — по требованию |
| Язык | TypeScript, `strict: true` | Единый контракт данных на фронт и формулы (docs/03) |
| Стили | Tailwind CSS | Токены дизайн-системы как конфиг, ноль ручного CSS-дублирования |
| Интерактив | React 19 (только внутри `client:*` островов; было React 18, апгрейд август 2026) | Экосистема форм/state для инструментов, ничего лишнего вне островов |
| Контент | Astro Content Collections + Zod-схемы | Типобезопасные статьи/справочники, ошибка контента = ошибка сборки |
| Бэкенд для account-фич | Supabase (Postgres + Auth + RLS), регион EU (Frankfurt) | Единственное, что реально требует сервера и авторизации (Ф4) |
| Хостинг | Cloudflare Pages + Pages Functions | См. сравнение выше |
| Формат данных CSDD | Периодическая xlsx/csv выгрузка → валидируемый ETL-скрипт → Postgres | Подтверждено заказчиком, не API |

## Последствия

- Разработчики должны понимать разницу между «страницей» и «островом» — это
  явно описано в CLAUDE.md как обязательный шаг при добавлении инструмента.
- Any account-based logic must live behind explicit auth checks inside the
  island, never in shared layout code — закреплено как architectural rule,
  проверяется на code review.
- Next.js остаётся рассмотренной, но отклонённой альтернативой; если продукт
  когда-то развернётся в «личный кабинет как основной сценарий» (не
  предусмотрено текущим ТЗ), этот ADR нужно пересмотреть явно, а не дрейфовать
  туда постепенно.
- **React 18 → 19, август 2026** (явный пересмотр, не дрейф): найден
  детерминированный баг `react-dom@18.3.1` `renderToPipeableStream`,
  вставляющий байты `0x00` в SSR-вывод на больших страницах (полное
  расследование — `docs/10-quality-gates.md` §2.1). React 19 чинит
  баг, но его клиентский рантайм тяжелее на ~14.7 KB gzip (измерено
  изолированно, не артефакт конфигурации проекта) — это подняло бюджет
  JS на странице с 60 до 75 KB (тот же §2.1 и §1/§2 того же документа).
  Явный, осознанный компромисс: целостность контента важнее на
  ~15 KB бюджета, решение принято пользователем, не по умолчанию.
